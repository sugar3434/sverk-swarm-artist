## <a id="what-it-does"></a>🎨 Что делает система

```
Промпт → vision (растр → палитра → черновой план)
       → agents (публичный диалог 4 личностей + координатор)
       → swarm  (координаты полотна + бесконфликтное расписание)
       → openclaw + fleet_coordinator (взлёт → покраска → посадка,
                                        постоянный контроль безопасности)
```

Всё это оркестрирует единая точка входа `mission_runner.py`.

## <a id="architecture"></a>🏗️ Архитектура

| Слой | Файлы | Требует ROS/железа? |
|---|---|---|
| Генерация изображения | `vision/prompt_to_bitmap.py`, `vision/bitmap_to_plan.py` | нет |
| Мультиагентный диалог | `agents/personas.py`, `agents/llm_client.py`, `agents/broadcast.py`, `agents/dialogue_engine.py` | нет |
| Координаты и анти-коллизии | `swarm/canvas_grid.py`, `swarm/conflict_scheduler.py` | нет |
| Мост к дронам (OpenCLaw) | `openclaw/drone_link.py`, `openclaw/commands.py`, `openclaw/middleware.py`, `openclaw/safety.py` | только `LiveDroneLink` |
| Координатор роя | `swarm/fleet_coordinator.py` | нет (работает с любым `DroneLink`) |
| Точка входа | `mission_runner.py` | нет в `--sim`, да в `--live` |

Полный контракт данных между модулями — в
[`docs/ARCHITECTURE_CONTRACT.md`](docs/ARCHITECTURE_CONTRACT.md). Журнал
изменений и обоснование каждого решения — в [`sverk_code.md`](sverk_code.md).

### <a id="agent-roles"></a>Роли агентов и дроны (Регламент, п. 2.1)

| Агент | Кредо | Цвет / дрон |
|---|---|---|
| @Академист | «Никакого хаоса — только порядок!» | Чёрный (контур) |
| @Экспрессионист | «К чёрту линии! Цвет должен кричать!» | Красный |
| @Минималист | «Одной капли достаточно. Меньше — значит больше» | Синий |
| @Детализатор | «Я пройду каждый сантиметр!» | Жёлтый/белый |

Диалог публично транслируется на stdout (в реальной инсталляции — на
проектор через захват окна терминала, см. docstring `agents/broadcast.py`) и
пишется в `logs/dialogue_transcript.jsonl` — стенограмма для судейской
коллегии («лучший диалог агентов»).

## <a id="installation"></a>⚙️ Установка

```bash
git clone https://github.com/sugar3434/sverk-swarm-artist.git
cd sverk-swarm-artist
py -3 -m venv .venv
.\.venv\Scripts\activate
python -m pip install --upgrade pip setuptools wheel
pip install -r requirements.txt
```

Для `--live` (реальный полёт) дополнительно нужен ROS 2 (Humble/Iron) и
собранный [sverk-ros2](https://github.com/sverk-tech/sverk-ros2) на борту
каждого дрона (`offboard_control`, `fmu_control`, `servo_control`,
`sverk_interfaces`) — они НЕ ставятся через pip, см. документацию sverk-ros2.

## <a id="drone-setup"></a>🛸 Подключение дронов-художников — пошаговая инструкция

Настоящее руководство предназначено для подготовки и физического подключения роя дронов-художников («Painters Swarm») перед выполнением творческой миссии. Каждая ступень содержит точные команды, объяснение назначения, руководство по решению возможных ошибок и метод проверки.

> ⚠️ **Важно:** Перед выполнением любых работ с реальными дронами убедитесь, что пропеллеры сняты на этапе настройки, а аппаратная пульт-радиосвязь (RC Transmitter) находится в руках пилота безопасности с включённым переключателем аварийной посадки!

### <a id="step-1"></a>Шаг 1: Клонирование репозиториев

* **Что делать:**  
  Клонируйте репозиторий низкоуровневого ROS 2 управления дронами `sverk-ros2` и репозиторий бортового агента PicoClaw `arhepelag_piko_claw`:
  ```bash
  git clone https://github.com/sverk-tech/sverk-ros2.git
  git clone https://github.com/KVALNF95/arhepelag_piko_claw.git
  ```

* **Зачем:**  
  - `sverk-ros2` содержит базовый стек пакетов ROS 2 для связи с PX4, интерфейсы `sverk_interfaces` и сервисы управления полётом и сервоприводом распыления (`offboard_control`, `fmu_control`, `servo_control`).
  - `arhepelag_piko_claw` (PicoClaw) содержит легкий бортовой агент для микрокомпьютера Raspberry Pi 5 на каждом дроне, который транслирует ИИ-команды OpenCLaw в физические действия дрона через MCP-протокол.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* `Permission denied (publickey)` или `Repository not found`.  
  - *Решение:* Проверьте подключение к сети Интернет. Если клонирование выполняется напрямую на бортовом компьютере Raspberry Pi 5 без SSH-ключей, используйте стандартный HTTPS URL: `https://github.com/...`.

* **Как проверить результат:**  
  Убедитесь, что оба каталога успешно появились на диске и содержат исходные файлы:
  ```bash
  ls -la sverk-ros2 arhepelag_piko_claw
  ```

### <a id="step-2"></a>Шаг 2: Установка зависимостей

* **Что делать:**  
  1. Установите ROS 2 (Humble Desktop/Base или Iron) на управляющую станцию и бортовые Raspberry Pi 5.
  2. Соберите пакет интерфейсов `sverk_interfaces`:
     ```bash
     cd sverk-ros2
     colcon build --packages-select sverk_interfaces
     source install/setup.bash
     cd ..
     ```
  3. Установите Docker и Docker Compose (для запуска контейнера бортового агента PicoClaw на Raspberry Pi 5):
     ```bash
     sudo apt-get update && sudo apt-get install -y docker.io docker-compose-plugin
     ```
  4. Создайте изолированное окружение Python для управляющей станции:
     ```bash
     python3 -m venv .venv
     source .venv/bin/activate
     pip install --upgrade pip setuptools wheel
     pip install -r requirements.txt
     ```

* **Зачем:**  
  Сборка `sverk_interfaces` генерирует Python-библиотеку для управления полётом, навигацией и клапанами распыления краски. Docker изолирует бортовой агент PicoClaw от ОС Raspberry Pi 5, предотвращая конфликты системных библиотек.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* `colcon: command not found` или `ModuleNotFoundError: No module named 'sverk_interfaces'`.  
  - *Решение:* Обязательно выполните `source /opt/ros/humble/setup.bash` перед запуском `colcon build`, а после сборки выполните `source install/setup.bash`.

* **Как проверить результат:**  
  Проверьте импорт пакета интерфейсов в Python:
  ```bash
  python3 -c "import sverk_interfaces; print('sverk_interfaces OK')"
  ```
  Команда должна без ошибок вывести `sverk_interfaces OK`.

### <a id="step-3"></a>Шаг 3: Настройка окружения (.env)

* **Что делать:**  
  1. Скопируйте файл с примером настроек в `.env`:
     ```bash
     cp .env.example .env
     ```
  2. Задайте параметры ИИ-модели, токена Hub и идентификаторы роя в `.env`:
     ```env
     # Настройки LLM для мультиагентного ИИ-диалога
     SVERK_LLM_API_KEY=sk-gjmHW2rkxnYl-N0dt5nVyg
     SVERK_LLM_BASE_URL=https://ai.sverk.io/v1
     SVERK_LLM_MODEL=gemma4-vlm

     # Настройки связи с центральным Hub и безопасности роя
     HUB_TOKEN=secret_swarm_token_2026
     HUB_URL=http://192.168.1.100:8080
     HANDLER_ID=team-7
     FLEET=painter
     ```

* **Зачем:**  
  Переменные `SVERK_LLM_*` определяют доступ к нейросетевому серверу, отвечающему за генерацию эскиза и художественную дискуссию личностей. `HUB_TOKEN`, `HUB_URL`, `HANDLER_ID` и `FLEET` гарантируют защиту от несанкционированного доступа и предотвращают перекрёстные помехи при одновременной работе нескольких команд в одной Wi-Fi сети.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* Ошибка `409 Conflict` или `401 Unauthorized` от сервера Hub при попытке подключения дрона.  
  - *Решение:* Убедитесь, что значение `HUB_TOKEN` и `HANDLER_ID` одинаковы на центральной станции управления (Hub) и в `.env` файлах каждого из бортовых компьютеров Raspberry Pi 5.

* **Как проверить результат:**  
  Проверьте правильность считывания параметров окружения скриптом:
  ```bash
  python3 -c "import os; from dotenv import load_dotenv; load_dotenv(); print('HANDLER_ID:', os.getenv('HANDLER_ID'))"
  ```

### <a id="step-4"></a>Шаг 4: Физическое подключение дронов-художников

* **Что делать:**  
  1. Разверните микрокомпьютеры Raspberry Pi 5 на 4 квадрокоптерах «Сверх».
  2. Назначьте каждому дрону свой уникальный ROS 2 namespace (пространство имён):
     - `/drone_black` — Чёрный контурный дрон (@Академист)
     - `/drone_red` — Красный фоновый дрон (@Экспрессионист)
     - `/drone_blue` — Синий минималистичный дрон (@Минималист)
     - `/drone_yellow` — Жёлтый детализирующий дрон (@Детализатор)
  3. Подключите бортовые Raspberry Pi 5 к общей локальной роутерной Wi-Fi сети 5 ГГц.
  4. Напольное полотно подготовьте, разложив карту ArUco-маркеров (`aruco_map`) по периметру площадки для абсолютной привязки координат.
  5. Выполните физическую привязку дрона методом **"Blink & Bind"**:
     - Откройте браузер и перейдите на страницу диспетчера Hub: `http://<hub_ip>:8080/fleet`.
     - В списке необработанных кандидатов нажмите **«💡 Blink»**. Hub отправляет сигнальную команду на выбранный дрон, и его светодиодная лента начнет задорно мигать (`/led` -> `set_effect`).
     - Визуально определив, какой из физических дронов замигал (например, дрон с синим баллончиком), нажмите **«✓ Bind»** и присвойте ему соответствующий `AGENT_ID` (например, `painter-blue`).
     - Привязка автоматически сохраняется в энергонезависимую память Raspberry Pi 5 в файл `/data/binding.json`.

* **Зачем:**  
  Использование уникальных namespaces гарантирует изоляцию навигационных топиков. Карта ArUco маркеров (`BRIDGE_FRAME="aruco_map"`) исключает дрейф координат в ходе полёта. Процедура "Blink & Bind" предотвращает случайные ошибки оператора при назначении цветов роя.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* Светодиодная лента не мигает при нажатии «💡 Blink» или дрон не видит ArUco маркеры.  
  - *Решение:* Проверьте питание светодиодной ленты и GPIO-подключение. Для ArUco маркеров убедитесь в достаточности освещения площадки и чистой линзе нижней камеры.

* **Как проверить результат:**  
  Проверьте наличие файла привязки на Raspberry Pi 5:
  ```bash
  cat /data/binding.json
  ```
  Файл должен содержать валидный JSON со статусом `"bound": true` и правильным `agent_id`.

### <a id="step-5"></a>Шаг 5: Проверка связи и готовности (Healthcheck & Телеметрия)

* **Что делать:**  
  1. Выполните HTTP-проверку работоспособности сервисов:
     ```bash
     curl -f http://localhost:8080/healthz
     ```
  2. Проверьте заряд аккумуляторов всех 4 дронов. Согласно **Регламенту (п. 2.6.7)**, заряд каждого аккумулятора перед началом попытки должен составлять **не менее 40%**.
  3. Запустите автоматическую предполётную проверку систем безопасности OpenCLaw:
     ```bash
     python3 -c "from openclaw.safety import SafetyMonitor; print('Safety Check Loaded')"
     ```

* **Зачем:**  
  Предполётный healthcheck гарантирует готовность всех узлов до взлёта. Жесткий лимит аккумулятора ≥40% предотвращает просадку питания в воздухе из-за дополнительного веса баллончика краски и обеспечивает запасы энергии на выполнение экстренной посадки.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* Предполётная проверка `preflight_check()` бракует дрон: `Battery pct 38% < 40.0%`.  
  - *Решение:* Замените аккумулятор на свежезаряженный. Не пытайтесь занижать порог в коде — запуск с зарядом менее 40% прямо нарушает п. 2.6.7 Регламента и ведет к дисквалификации попытки!

* **Как проверить результат:**  
  Проверьте статус батареи и готовности через ROS 2 топик:
  ```bash
  ros2 topic echo /drone_black/fmu_control/status --once
  ```
  Значение `battery_pct` должно быть `≥ 40.0`, а `armed` равно `False`.

### <a id="step-6"></a>Шаг 6: Первый запуск в симуляции и переход к реальному полёту

* **Что делать:**  
  1. **Шаг 6A (Симуляция `--sim`):** Проведите тестовую генерацию и проверьте построение безопасной траектории без взлёта дронов:
     ```bash
     python3 mission_runner.py --prompt "нарисуй закат над морем" --sim
     ```
     Или с помощью полного студийного эмулятора PicoClaw:
     ```bash
     cd arhepelag_piko_claw && make demo-studio
     ```
  2. **Шаг 6B (Реальный полёт `--live`):** Убедившись в правильности полученного рисунка и отсутствии коллизий в логах, переходите к полёту:
     - Запустите Docker-контейнер бортового агента на каждом Raspberry Pi 5:
       ```bash
       docker compose -f docker-compose.drone.yml up -d
       ```
     - Запустите миссию на управляющем ПК в режиме реального времени:
       ```bash
       python3 mission_runner.py --prompt "нарисуй закат над морем" --live \
         --namespaces drone_black:/drone_black,drone_red:/drone_red,drone_blue:/drone_blue,drone_yellow:/drone_yellow \
         --cols 10 --rows 10 --canvas-size-m 2.4
       ```

* **Зачем:**  
  Симуляция `--sim` полностью исключает риск повреждения оборудования при настройке и экономит краску в баллончиках. Режим `--live` подключает реальные исполнительные механизмы `LiveDroneLink` только после проверки всей логической цепочки.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* `LiveDroneLink error: sverk_interfaces module not found`.  
  - *Решение:* Переключитесь на терминал с подгруженным окружением ROS 2 (`source sverk-ros2/install/setup.bash`).

* **Как проверить результат:**  
  Убедитесь, что в каталоге `logs/` созданы файлы `openclaw_events.jsonl` и `dialogue_transcript.jsonl`, а веб-панель `http://localhost:8080/studio` отображает активную фазу `EXECUTE`.

### <a id="step-7"></a>Шаг 7: Подготовка баллончиков краски и сервоприводов клапанов

* **Что делать:**  
  1. Закрепите аэрозольный баллончик с краской соответствующего цвета (Чёрный, Красный, Синий, Жёлтый) в легком быстросъёмном держателе на раме дрона.
  2. Установите сервопривод нажатия на клапан распыления и подключите его к управляющему каналу GPIO.
  3. Задайте углы работы сервопривода в параметрах `bridge/ros2/bridge_node.py` или файле конфигурации:
     - `SPRAY_ON_DEG`: угол нажатия на клапан (по умолчанию `60.0°` или `90.0°`).
     - `SPRAY_OFF_DEG`: исходный угол закрытого клапана (`0.0°`).
  4. Отрегулируйте механическую тягу так, чтобы в положении `0.0°` клапан был полностью разгружен, а при повороте на `SPRAY_ON_DEG` происходило уверенное распыление.
  5. Проверьте аппаратный механический fail-safe: сервопривод снабжается возвратной пружиной клапана, которая при отключении питания автоматически возвращает сервопривод в положение `0.0°`.

* **Зачем:**  
  Точная настройка хода сервопривода предотвращает подтёки краски на холсте. Гарантированное закрытие клапана в состоянии `0.0°` предотвращает неконтролируемое распыление при срабатывании программного Kill Switch или обрыве связи.

* **Что может пойти не так (Ошибки и их решение):**  
  - *Ошибка:* Сервопривод непрерывно жужжит в закрытом состоянии или краска продолжает стравливаться после закрытия.  
  - *Решение:* Скорректируйте положение качалки сервопривода или немного уменьшите базовый угол `SPRAY_OFF_DEG`, чтобы снятие давления с клапана происходило полностью.

* **Как проверить результат:**  
  Проведите тестовый импульс распыления через ROS 2 топик:
  ```bash
  ros2 topic pub --once /drone_black/servo_control/target_angle_deg std_msgs/msg/Float32 "{data: 60.0}"
  ros2 topic pub --once /drone_black/servo_control/target_angle_deg std_msgs/msg/Float32 "{data: 0.0}"
  ```
  Баллончик должен кратковременно распылить краску во время отправки `60.0` и мгновенно прекратить распыление после команды `0.0`.

## <a id="execution"></a>🚀 Запуск

Сухой прогон без ROS и без дронов (проверка логики, безопасно запускать где
угодно):

```bash
python3 mission_runner.py --prompt "нарисуй солнце над горами" --sim
```

Пример вывода: генерация растра → черновой план N задач → публичный диалог
4 личностей + координатор → бесконфликтное расписание → синхронный взлёт →
выполнение → синхронная посадка, с полным логом в `logs/`.

Реальный полёт (на площадке соревнования, 4 дрона, каждый в своём
ROS-namespace):

```bash
python3 mission_runner.py --prompt "<промпт судей>" --live \
  --namespaces drone_black:/drone_black,drone_red:/drone_red,drone_blue:/drone_blue,drone_yellow:/drone_yellow \
  --cols 10 --rows 10 --canvas-size-m 2.4
```

Опции: `--cols/--rows` (разрешение сетки полотна), `--canvas-size-m` (размер
полотна, Регламент п. 2.7: не менее 2×2 м), `--dialogue-rounds` (раунды
обсуждения), `--log-dir`.

Реальная LLM вместо офлайн-заглушки (опционально, с автоматическим fallback
на офлайн-агентов при сбое сети):

```bash
export SVERK_LLM_API_KEY=...        # обязателен
export SVERK_LLM_BASE_URL=...       # опционально, по умолчанию OpenAI
export SVERK_LLM_MODEL=gpt-4o-mini  # опционально
```

## <a id="safety"></a>🛡️ Безопасность (Регламент, разделы 2.6 и 2.8)

Реализовано в `openclaw/safety.py` + `swarm/fleet_coordinator.py`:

- Проверка заряда каждого дрона ≥ 40% перед допуском к попытке (п. 2.6.7).
- Высота полёта ограничена 4 м, проверяется перед КАЖДОЙ навигационной
  командой, а не только при взлёте (п. 2.6.2).
- Лимит попытки 15 минут с резервом на гарантированную посадку — сторожевой
  поток прерывает миссию заранее, а не после истечения бюджета (п. 2.2).
- Программный KILL SWITCH (`SafetyMonitor.kill_switch`) — дублирующий канал
  поверх штатного аппаратного RC-перехвата `offboard_control`
  (`check_kill_switch`), пробует несколько каналов остановки на каждом дроне
  и не прерывается на первом отказавшем дроне (п. 2.6.11, 2.8.5).
- Анти-коллизии: `swarm/conflict_scheduler.py` гарантирует, что задачи
  разных дронов на близких ячейках полотна никогда не выполняются
  параллельно по времени — проверено на 40 случайных наборах по 30-40 задач
  (`tests/test_review_a_safety.py::test_schedule_random_no_conflicts`).
- Мягкая деградация на всех уровнях: сбой одного дрона/одной команды/одной
  реплики LLM не останавливает всю попытку — см. `sverk_code.md` для деталей.

> ⚠️ **Предупреждение о безопасности:** Аппаратный радиоперехват управления на пульте оператора (`check_kill_switch: true`) является ПЕРВИЧНЫМ средством обеспечения безопасности. Программный Kill Switch слоя OpenCLaw выступает резервным дублирующим контуром.
