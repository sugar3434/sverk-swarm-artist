# Журнал изменений кода — sverk-swarm-artist

Этот файл — единый журнал того, что происходит в коде проекта «Рой
дронов-художников» (соревнование «Архипелаг 2026», регламент см.
`docs/ARCHITECTURE_CONTRACT.md`), и памятка, как его поправить в случае чего.
Записи идут в хронологическом порядке (снизу — новее... нет, здесь сверху
вниз по факту написания, дата — везде 2026-07-27, сессия одна).

## 2026-07-27 — Архитектура и контракт модулей

- Изучен реальный API `sverk-ros2` (клонирован из
  [github.com/sverk-tech/sverk-ros2](https://github.com/sverk-tech/sverk-ros2)):
  `sverk_interfaces.init(...)`, `drone.control.*` (navigate/navigate_wait/land/
  get_telemetry/get_status/emergency_stop/return_to_launch), `drone.fcu.*`
  (arm/disarm/force_disarm/kill_switch/reboot), `drone.gpio.servo_*`
  (сервопривод клапана краски).
- Обнаружено, что в самом sverk-ros2 уже есть прообраз OpenCLaw —
  `web/ros2_mcp` (HTTP/MCP-мост с policy-движком, `llm_query`/`vlm_query`,
  описание: «HTTP server for picoclaw integration»). Наш `openclaw/` архитектурно
  повторяет эту идею на уровне высокоуровневых команд (`openclaw/commands.py`).
- Зафиксирован контракт данных в `common/schema.py` (`PaintTask`, `Plan`,
  `DialogueTurn`, `ScheduledTask`, `COLORS`) — единственный файл, который
  НЕЛЬЗЯ менять без пересогласования всех модулей.
- Работа разделена на независимые модули (см. `docs/ARCHITECTURE_CONTRACT.md`)
  и распараллелена между несколькими агентами/моделями:
  - `vision/` + `swarm/canvas_grid.py` + `swarm/conflict_scheduler.py` —
    один поток разработки (без rclpy, полностью офлайн-тестируемый);
  - `agents/` (мультиагентный LLM-диалог 4 личностей + координатор) —
    второй, полностью независимый поток;
  - `openclaw/` (мост к sverk_interfaces) + `swarm/fleet_coordinator.py` +
    `mission_runner.py` — интеграционный слой, написан ведущим агентом,
    так как требует точного соответствия исследованному API sverk-ros2.

## 2026-07-27 — Критический фикс: цветовые заливки в vision/prompt_to_bitmap.py

**Найдено при первом сквозном прогоне `mission_runner.py`:** все фигуры
рисовались ТОЛЬКО чёрным контуром без заливки. После квантования по палитре
это означало, что практически 100% закрашенных пикселей граничили с фоном →
`detect_outline_cells` помечал их ВСЕ как контур → `bitmap_to_plan`
принудительно красил всё в чёрный. Итог: 3 из 4 дронов (red/blue/yellow)
не получали ни одной задачи — критическая потеря баллов за «одновременный
взлёт дронов с роевым взаимодействием» (дроны хоть и взлетали, но не
участвовали в рисовании) и просто нелогичный результат для соревнования
на 4 цвета краски.

**Фикс:** каждая фигура (`_draw_sun`, `_draw_mountains`, `_draw_heart`,
`_draw_star`, `_draw_house`, `_draw_tree`, `_draw_flower`,
`_draw_animal_face`, `_draw_wave`, `_draw_abstract`) теперь заливается ОДНИМ
из 4 цветов палитры (`fill=...`), а чёрный контур рисуется поверх заливки
(`outline="black"`). Так реальные цветные области попадают в растр и
корректно распределяются между дронами; контур остаётся минорной, а не
подавляющей долей ячеек.

Проверка: `python3 -c "... Counter(цветов) ..."` на промпте «нарисуй солнце
над горами», сетка 12x12 → `{'blue': 25, 'yellow': 24, 'black': 10, 'red': 2}`
(было: 100% black). Полный прогон `mission_runner.py --sim` → все 4 дрона
получают задачи.

- `Broadcaster(log_path=None)` и автосоздание глубоко вложенного каталога
  лога — проверено, уже работало корректно, регрессия не нужна.

## 2026-07-27 — Review pass A (safety/regulation focus), модели: claude_opus_5_0

Ревью критического пути (`openclaw/`, `swarm/`, `mission_runner.py`) на
соответствие Регламенту и на многопоточные гонки. Найденные и исправленные
проблемы (важно знать при доработке — «как поправить в случае чего»):

1. **п. 2.2 (лимит 15 минут):** `check_time_budget()` раньше срабатывал
   РОВНО в момент истечения бюджета — посадка гарантированно выходила за
   лимит. Добавлен `LANDING_RESERVE_S = 30.0` (`openclaw/safety.py`):
   `remaining_flight_s()` = бюджет − резерв на посадку − прошедшее время;
   `check_time_budget(extra_s=...)` не пускает задачу, которая не успеет
   закончиться до дедлайна с учётом резерва. В `swarm/fleet_coordinator.py`
   добавлен **сторожевой поток** (`_watchdog`, период `WATCHDOG_PERIOD_S=0.5с`),
   который опрашивает бюджет НЕЗАВИСИМО от того, чем заняты потоки дронов —
   раньше проверка была только перед стартом очередной задачи дрона, и если
   задача длилась минуту, лимит обнаруживался с большой задержкой.
2. **п. 2.6.2 (высота ≤ 4 м):** раньше проверялась только при взлёте.
   Теперь `openclaw/middleware.py._check_altitude()` проверяет высоту ПЕРЕД
   КАЖДОЙ командой с целевой z (takeoff/navigate/paint_zone) — middleware
   это единая точка, через которую проходят все команды, поэтому это
   правильное место для «предохранителя». Дополнительно `mission_runner.py`
   проверяет ВЕСЬ план целиком ДО взлёта (см. `too_high` в `run_mission`).
3. **Race conditions в `fleet_coordinator.py`:** несколько потоков дронов +
   сторожевой поток могли параллельно вызвать `abort()`/KILL SWITCH.
   Добавлены `_abort_lock` (идемпотентный `abort()`, реальный kill_switch
   уходит в рой ровно один раз) и `_kill_lock` внутри
   `SafetyMonitor.kill_switch()` (сериализация относительно ROS-сервисов).
4. **`KeyError`/`AttributeError` внутри потоков дронов** молча убивали поток
   (отчёт показывал 0 провалов, дрон «зависал» без объяснения):
   - незнакомый `drone_id` в расписании → `report.skipped_unknown_drone`
     вместо `KeyError` (`fleet_coordinator.run_schedule`);
   - незнакомый `drone_id` в командах → `OpenClaw._get_link()` возвращает
     `None` с логом вместо `KeyError` (`openclaw/middleware.py`);
   - задача без мировых координат (x/y/z=None) раньше тихо летела в (0,0,0)
     — теперь пропускается с `report.skipped_unsafe`;
   - весь `_run_drone` обёрнут в `try/except BaseException`, чтобы ЛЮБАЯ
     непредвиденная ошибка фиксировалась в отчёте, а не убивала поток тихо.
5. **`LiveDroneLink` без успешного `connect()`:** вызовы падали
   `AttributeError: 'NoneType' object has no attribute ...`, который НЕ
   ловится обработчиками `(DroneLinkError, TimeoutError, RuntimeError)` в
   middleware. Добавлен `_require_link()`, бросающий `DroneLinkError` —
   единообразную, ожидаемую всеми уровнями ошибку.
6. **`LiveDroneLink.get_status()`:** вызывал
   `drone.control.get_telemetry(timeout=2.0)`, а у реального API
   `get_telemetry` принимает `frame_id`, но НЕ `timeout` — на настоящем
   железе это гарантированно `TypeError` при каждой проверке заряда
   (п. 2.6.7 стало бы невозможно проверить). Исправлено на
   `get_telemetry(frame_id="map")`.
7. **`LiveDroneLink.emergency_stop()`** раньше не давал знать вызывающей
   стороне, что ОБА канала (offboard emergency_stop и fcu.kill_switch)
   провалились — журнал показывал «OK» для несработавшего KILL SWITCH
   (ложное доказательство для судей). Теперь бросает `DroneLinkError`, если
   оба канала не сработали; `SafetyMonitor.kill_switch()` пробует и третий
   резервный канал — `land()` — и возвращает список дронов, которых не
   удалось остановить НИКАК (для честного отчёта).
8. **Клапан краски мог остаться открытым в воздухе:** в `land()` закрытие
   клапана раньше было в одном `try/except` с самой посадкой — если
   `servo_set_angle` падал, `land()` вообще не вызывался. Разделено на два
   независимых `try/except`: закрытие клапана best-effort, посадка — отдельно
   и обязательно.
9. **`conflict_scheduler.schedule()` — семантика окна:** раньше время
   перелёта добавлялось ДО `start_offset_s`, из-за чего реальный дрон (который
   в `fleet_coordinator` ждёт ровно до `start_offset_s`, а потом ЛЕТИТ)
   отставал от расписания на время перелёта — расписание перестаёт быть
   верной гарантией бесконфликтности в реальном времени. Исправлено: окно
   `[start_offset_s, end_offset_s)` теперь ВКЛЮЧАЕТ перелёт (см. docstring
   `schedule()`). Добавлена единая константа скорости перелёта
   `openclaw.commands.PAINT_TRAVEL_SPEED_MPS`, используемая И планировщиком,
   И исполнителем — раньше это были два разных default-значения (0.4 у
   планировщика, 0.35 у `paint_zone`), что тоже рассинхронизировало реальность
   с расписанием.
10. **`build_fleet()` в `mission_runner.py`:** раньше сбой `connect()` одного
    дрона ронял всю попытку целиком, а уже подключённые дроны не закрывались
    (висящие ROS-подписки, включённые сервоприводы). Теперь: сбойный дрон
    аккуратно закрывается и исключается из роя, миссия продолжается с
    оставшимися; исключение — только если не подключился НИ ОДИН дрон.
    Цвета без подключённого дрона исключаются из плана в `run_mission()`.
11. **Свойство бесконфликтности проверено на случайных данных:** тест
    `test_schedule_random_no_conflicts` прогоняет 40 случайных наборов по
    30-40 задач на сетке 10x10 — `validate_no_conflicts()` пуст во всех
    случаях.
12. Добавлен `tests/test_review_a_safety.py` (13 тестов, один мелкий баг —
    несуществующий цвет `"green"` в тестовых данных — исправлен ведущим
    агентом при финальной интеграции).

Итог полного прогона после интеграции обеих ревизий: **54 passed**.

## Как поправить в случае чего (шпаргалка для будущих правок)

- **Меняете расписание/скорость перелёта?** Меняйте
  `openclaw/commands.py::PAINT_TRAVEL_SPEED_MPS` — используется И
  планировщиком (`swarm/conflict_scheduler.py`), И исполнителем
  (`openclaw/middleware.py::paint_zone`). Если поменять только в одном месте —
  расписание разойдётся с реальностью и гарантия бесконфликтности сломается.
- **Меняете лимит времени попытки/резерв на посадку?**
  `openclaw/safety.py::ATTEMPT_BUDGET_S` / `LANDING_RESERVE_S`. Сторожевой
  поток в `fleet_coordinator.py` (`WATCHDOG_PERIOD_S`) подхватит изменение
  автоматически.
- **Добавляете новую высокоуровневую команду?** Добавьте dataclass в
  `openclaw/commands.py`, метод в `openclaw/middleware.py::OpenClaw` (не
  забудьте `_check_altitude`, если команда двигает дрон), и вызов из
  `swarm/fleet_coordinator.py`, если она должна планироваться по расписанию.
- **Хотите настоящую LLM вместо офлайн-заглушки?** Задайте переменные
  окружения `SVERK_LLM_API_KEY` (+ опционально `SVERK_LLM_BASE_URL`,
  `SVERK_LLM_MODEL`) — `agents/llm_client.py::build_llm_client()` подключит
  `OpenAICompatibleClient` с автоматическим fallback на офлайн-клиент при
  любом сбое сети.
- **Переходите с `--sim` на `--live` (реальные дроны)?** Нужно ROS 2 окружение
  с собранным `sverk-ros2` (offboard_control/fmu_control/servo_control на
  борту каждого дрона в своём namespace) — см. README.md, раздел
  «Установка» и «Запуск на реальном рое». `mission_runner.py --live
  --namespaces drone_black:/ns1,...` — namespace на дрон обязателен.
- **Что-то падает в потоке дрона и отчёт не объясняет почему?**
  Смотрите `logs/openclaw_events.jsonl` (латентность и причина каждой
  команды) и `report.per_drone[drone_id].abort_reason` — весь код
  спроектирован так, чтобы НИКАКАЯ ошибка не убивала поток без записи причины
  (см. п. 4 ревью A выше).
